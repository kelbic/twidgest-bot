## 1. Что строим (продукт в двух абзацах)

Бот-маркетолог — **личный ассистент основателя по продажам**, отдельный
Telegram-бот (свой токен, свой процесс, своя БД), доступный только админу.
Он автоматизирует всё *до* кнопки «отправить»: находит и обогащает лиды
(Telegram-каналы 200–5000 подписчиков в нишах, которые Twidgest покрывает),
оценивает «ведут ли канал вручную», генерирует **персональный демо-дайджест
по нише лида** силами существующего пайплайна Twidgest и пишет черновик
персонализированного сообщения. Результат — карточка в чате у основателя:
метрики, скоринг, готовый текст, кнопки «✅ Одобрить / ✏️ Править / ❌ Скип».

Отправляет сообщения **только человек, вручную, со своего аккаунта**.
Бот ведёт мини-CRM: статусы лидов, воронку, напоминания о фоллоу-апах.
Целевой режим работы основателя: 20–30 минут в день на разбор карточек
и отправку 10–20 сообщений.

## 2. Жёсткие правила — нарушать нельзя ни при каких условиях

1. **Никакой автоматической отправки исходящих сообщений незнакомым людям.**
   Запрещены: userbot'ы (MTProto-клиенты: Telethon, Pyrogram и т.п.) от имени
   человеческого аккаунта, любые массовые рассылки, любая «полуавтоматическая»
   отправка. Bot API боту и так не позволяет писать первым — не обходить это.
   Единственный получатель сообщений бота — админ (`ADMIN_USER_ID`).
2. **Прод не трогать.** `twidgest-bot.service` не перезапускать, файлы
   существующего бота (`bot/`, `workers/`, `core/`, `db/`, `main.py`,
   `config.py`, `prompts.py`) **не редактировать** — только импортировать.
   Прод-базу `twidgest.db` не открывать на запись (чтение не требуется вовсе).
   Все изменения — только добавление новых файлов в `marketing/`, `tests/`,
   `deploy/`, `docs/`.
3. **Секреты**: новые токены только через `.env`, никаких значений в коде и
   в git. В git не коммитить `.env`, `marketing.db` и её бэкапы.
4. **Черновики сообщений**: без ссылок в первом сообщении (антиспам-эвристики
   Telegram), без обмана и «прогревов», честное представление («я сделал бота,
   который...»). В каждом черновике — персонализация по реальным фактам
   из канала лида.
5. **Opt-out свят**: ответ «не пишите мне» → статус `optout` + blacklist навсегда.
6. **Бюджеты жёсткие** (раздел 9): LLM и twitterapi.io капятся в коде, не
   только в конфиге по умолчанию.
7. Если что-то из задания невозможно на этом VPS (нет доступа, нет пакета) —
   не изобретать обходной путь, нарушающий пп. 1–3, а зафиксировать блокер
   в `marketing/README.md` и продолжить с остальным.

## 3. Что уже есть и что переиспользовать

Репозиторий twidgest-bot лежит на этом VPS (найди корень: там `main.py`,
`config.py`, systemd-юнит `deploy/twidgest-bot.service`). Работает venv
с зависимостями из `requirements.txt` (aiogram 3, SQLAlchemy 2 async,
aiosqlite, aiohttp, apscheduler). `.env` содержит рабочие
`OPENROUTER_API_KEY`, `TWITTERAPI_KEY`, `ADMIN_USER_ID` и др. — переиспользуй.

Модули для импорта (изучи перед проектированием):

| Модуль | Что брать |
|---|---|
| `core/llm_client.py` | `OpenRouterClient`, `suggest_sources(topic, count)` — подбор X-аккаунтов по теме; `_call_with_retry(system, user, ...)` — низкоуровневый вызов (приватный API, оберни в свой хелпер `marketing/llm.py`, чтобы была одна точка связки) |
| `workers/source_scout.py` | `prevalidate_candidates(...)` — проверка авторов по реальным твитам, `apply_topic_relevance(...)` — доля твитов по теме |
| `core/twitter_cache.py` | `TwitterCache` — создай **один** инстанс на процесс marketing-бота и передавай всюду (в проде есть анти-паттерн трёх независимых кэшей — не повторяй) |
| `prompts.py` | `build_digest_prompt(niche, legal_rf=...)` — системный промпт дайджеста для демо |
| `workers/publisher.py` | `_build_digest_with_prompt(llm, tweets, system_prompt)` — образец сборки дайджеста (не импортируй приватную функцию — скопируй паттерн в `marketing/demo.py`) |

Известные грабли прода (учитывай):
- `config.Config()` исполняется на **импорте** в ряде модулей (`core/plan.py`,
  воркеры) — импорт требует полный набор env-переменных; в тестах —
  `monkeypatch.setenv` в `conftest.py`.
- Формат даты twitterapi.io: `'Tue Jun 09 19:33:45 +0000 2026'`,
  парсер — `Tweet.parsed_created_at` (`core/twitter_client.py`).
- twitterapi.io биллит за возвращённые твиты (минимум 15 кредитов/вызов) —
  каждый лишний fetch стоит денег.

## 5. Схема БД (SQLite, SQLAlchemy async — по образцу `db/models.py`)

```python
class Lead(Base):
    id: int                      # PK
    channel_username: str        # без @, unique
    title: str | None
    description: str | None
    subscribers: int | None
    niche: str | None            # свободная строка ("F1", "AI news", ...)
    source: str                  # 'manual' | 'import' | 'tgstat' | 'kwork'
    contact: str | None          # @админа из описания канала, если найден
    status: str                  # new → enriched → qualified → approved →
                                 # contacted → replied → trial → paid
                                 # | dead | optout   (терминальные)
    score: int | None            # 0-100, итог квалификации
    score_reason: str | None     # короткое объяснение (для карточки)
    posts_per_week: float | None
    gap_cv: float | None         # коэффициент вариации интервалов (см. 6.2)
    last_post_at: datetime | None
    demo_text: str | None        # персонализированное демо (или ссылка на niche_demo)
    draft_text: str | None       # текущий черновик сообщения
    contacted_at: datetime | None
    next_followup_at: datetime | None
    notes: str | None            # свободные заметки основателя (/note)
    created_at, enriched_at: datetime

class LeadEvent(Base):           # журнал: что и когда происходило с лидом
    id, lead_id (FK, index), event: str, payload: str | None, created_at

class NicheDemo(Base):           # кэш демо-дайджестов ПО НИШЕ (не по лиду!)
    id, niche_key: str (unique, normalized), demo_text: str,
    sources_json: str, created_at   # TTL 7 дней — старше не показывать, перегенерировать

class Blacklist(Base):
    id, channel_username: str (unique), reason: str, created_at
```

Дедупликация: `channel_username` unique; повторный импорт существующего лида —
no-op с записью в LeadEvent.

## 6. Пайплайн

### 6.1 Discovery (MVP — ручной ввод; API-интеграции потом)
- `/addlead @channel [ниша]` — добавить один канал.
- `/import` — следующим сообщением список: по одному `@channel [ниша]` на строку
  (или CSV `username,niche`). Валидация username-регексом, дедуп, blacklist-фильтр.
- Заглушка `marketing/sources_tgstat.py` с TODO-интерфейсом `fetch_leads(niche) -> list[...]`
  — подключение TGStat API отдельным этапом, НЕ в MVP.
- Kwork/fl.ru в MVP не парсить (у площадок свои правила) — основатель добавляет
  такие лиды руками через `/addlead`.

### 6.2 Enrichment (воркер, каждый час, батч ≤5 лидов со status=new)
Источник данных — **публичное веб-превью** `https://t.me/s/<username>`
(обычный HTTPS GET, aiohttp, без авторизации; это не userbot). Парсить:
- посты: блоки `tgme_widget_message`, у каждого `<time datetime="...">` —
  собрать список дат (превью отдаёт ~20 последних постов);
- подписчики: `tgme_page_extra` («N subscribers»);
- заголовок/описание страницы (в описании часто контакт админа — вытащить
  первый @username, не совпадающий с каналом).

Метрики поверх дат постов (та же математика, что в задизайненном скоринге
регулярности скаута):
```python
gaps = разности соседних дат в часах, floor 1 минута
posts_per_week, median_gap_hours
gap_cv = pstdev(gaps) / mean(gaps)     # ВЫСОКИЙ cv = рваный ручной постинг = ХОРОШИЙ лид
last_post_at
```
Вежливость: ≤1 запрос/сек, кэш ответа 24ч, таймаут 10с, ретрай один.
Если превью недоступно (канал приватный/без превью) → status=`enriched`
с пустыми метриками и пометкой в карточке «обогатить не удалось — оцени руками».
Ошибки не роняют батч (per-lead try/except — как в прод-воркерах).

### 6.3 Qualification (сразу после enrichment)
Эвристики (без LLM), каждая даёт вклад в score 0–100:
- канал жив: `last_post_at` не старше 14 дней (иначе −40);
- размер: 200–5000 подписчиков — цель; <200 → −20; >20000 → −30 (не наша лига в MVP);
- **признак «ведут вручную»**: `gap_cv ≥ 1.2` и постинг в разное время суток → +25
  (ровный автопостинг раз в сутки в 09:00 — уже автоматизирован, лид слабый);
- контакт админа найден → +10;
- ниша указана/угадана и входит в сильные для Twidgest (AI, crypto, спорт/F1,
  наука, longevity, гейминг, стартапы — Twitter-покрытие 90%+) → +15,
  узкая русская региональная ниша → −25 (Twitter её не покрывает).

Затем один LLM-вызов (батчем до 5 лидов, дешёвая модель — как
`apply_topic_relevance` в скауте): по описанию и заголовкам постов оценить
(JSON) `{niche_guess, fit_0_100, hook}` — где hook — конкретная зацепка для
персонализации («у вас 4 дня не было постов», «вы вручную переводите англоязычные
новости»). Fail-open: LLM упал → квалификация по эвристикам, hook пустой.
Итог: `score`, `score_reason`; score < 40 → status=`dead` (авто),
иначе `qualified` → генерируется карточка.

### 6.4 Demo (по требованию, с кэшем по нише)
`demo.py`: нормализовать нишу лида → ключ; если в `niche_demos` есть свежий
(≤7 дней) — взять его. Иначе, если дневной кап демо не исчерпан:
`suggest_sources(topic)` → `prevalidate_candidates` (min_likes=20, min_retweets=0)
→ взять топ-3 автора → из уже полученных твитов собрать дайджест по паттерну
`_build_digest_with_prompt` с `build_digest_prompt(niche, legal_rf=True)`
→ сохранить в кэш. Демо на карточке помечается: «сгенерировано по нише,
проверь перед отправкой».

### 6.5 Copywriting
`copywriter.py`, один LLM-вызов на лид. Требования к черновику:
- русский, 350–600 знаков, без ссылок, без эмодзи-спама (максимум один);
- структура: персональная зацепка из hook/метрик → одно предложение, кто я и
  что сделал → предложение прислать демо-дайджест по их нише → вопрос;
- тон: разработчик-одиночка пишет коллеге, не «менеджер по продажам»;
- запрещено: обещания цифр роста, «уникальная возможность», давление.

Системный промпт (заготовка, доработай):
```
Ты пишешь короткое первое сообщение админу Telegram-канала от лица
разработчика-одиночки. Продукт: бот, который сам ведёт тематический канал —
находит виральные посты в X/VK по нише, фильтрует и переписывает на русский.
Пиши по-русски, 350–600 знаков, БЕЗ ссылок. Начни с конкретного наблюдения
о канале получателя (используй hook и метрики из входа). Один факт о продукте.
Предложи прислать готовый демо-дайджест по их теме. Закончи коротким вопросом.
Никакого напора, никаких обещаний роста. Верни только текст сообщения.
```
Фоллоу-ап (для 6.7): 150–300 знаков, мягкий, максимум один, через 4 дня;
если снова тишина → status=`dead`.

### 6.6 HIL-карточка (ядро UX)
Новые qualified-лиды бот пушит админу сам (батч не более 10/день, остальное
копится в очереди `/queue`). Карточка:
```
🎯 @channel — «Заголовок» (ниша, N подписчиков)
score 72: жив (посты 2 дн назад), рваный постинг (cv 1.8 → вручную), контакт найден
≈4 поста/нед · последний 2 дн назад · hook: «переводят англоязычные AI-новости руками»

📝 Черновик:
<draft_text>

🎁 Демо по нише: готово (или: [🎁 Сгенерировать демо])
[✅ Одобрить] [✏️ Править] [🔁 Другой черновик] [❌ Скип] [🚫 Blacklist]
```
- ✅ Одобрить → бот присылает финальный текст **отдельным чистым сообщением**
  (удобно копировать с телефона) + демо вторым сообщением + кнопку
  `[📤 Отправлено]` → по нажатию status=`contacted`, `contacted_at=now`,
  `next_followup_at=now+4d`.
- ✏️ Править → FSM: следующим сообщением админ шлёт правки («короче», «убери
  про VK», либо готовый текст) → LLM переписывает или текст берётся как есть.
- ❌ Скип → `dead`; 🚫 → `optout` + Blacklist.

### 6.7 CRM-воркер (ежедневно, 10:00 МСК)
- лиды `contacted` с `next_followup_at <= now` → карточка «пора фоллоу-апить»
  с черновиком фоллоу-апа (те же кнопки);
- дайджест-сводка админу: сколько new/qualified в очереди, воронка за неделю.

Команды: `/queue` (следующая карточка), `/leads [status]` (список, счётчики),
`/lead <id>` (карточка любого лида), `/mark <id> replied|trial|paid|dead`
(ручное движение по воронке; `trial`/`paid` — момент истины для метрик),
`/note <id> <текст>`, `/stats` (воронка new→contacted→replied→trial→paid,
конверсии в %, среднее время ответа), `/pause` / `/resume` (воркеры),
`/export` (CSV всех лидов в чат).

## 8. Деплой

`deploy/twidgest-marketing.service` по образцу прод-юнита, но:
- `Restart=always`;
- выделенный пользователь (не root), `NoNewPrivileges=yes`,
  `ProtectSystem=strict` + `ReadWritePaths=` на директорию с `marketing.db`
  (если прод-юнит работает от root — всё равно сделай новый юнит правильно);
- тот же WorkingDirectory (корень репо) и venv-python, `EnvironmentFile=.env`.

Юнит **создать и включить только после** того, как основатель добавит
`MARKETING_BOT_TOKEN` в `.env` (раздел 12).

## 9. Бюджет (ориентир, чтобы капы имели смысл)

- LLM: квалификация ~5 батчей/день + 10 черновиков + правки ≈ 20–40 вызовов
  дешёвой модели ≈ центы/день. Кап 100 — потолок с запасом.
- twitterapi.io: только демо. 1 демо = suggest(12) → превалидация ≤12 fetch'ей
  × ~20 твитов ≈ 3–4K кредитов ≈ $0.03–0.05. Кап 5 демо/день + кэш по нишам
  → доллары в месяц. Кэш по нише обязателен: 50 лидов в нише «AI» = 1 демо.
- t.me/s/: бесплатно.

## 10. Тесты и верификация

Обязательные unit-тесты (pytest, без сети и без LLM — фикстуры):
1. `test_marketing_enrich.py`: парсер t.me/s/ на сохранённом HTML-снапшоте
   (2 фикстуры: обычный канал, канал без превью) — даты, подписчики, контакт;
2. `test_marketing_qualify.py`: эвристики скоринга — мёртвый канал, ровный
   автопостер (низкий cv), рваный ручной (высокий cv), крошечный, гигантский;
   LLM-часть мокается, проверить fail-open.

Ручная верификация перед сдачей (dry-run):
- поднять бота локально (`python -m marketing.main`) с тестовым токеном;
- `/addlead` на 2–3 реальных публичных канала → в течение цикла приходит
  карточка с метриками, скорингом, черновиком;
